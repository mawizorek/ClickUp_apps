## Standards

### Naming Conventions

| Layer | Pattern | Example |
|-------|---------|--------|
| Table | PascalCase, plural for collections, singular for config | `Loans`, `PropertySUMMARIES`, `GLOBAL_USE_VARIABLES` |
| Field | snake_case, prefixed with table abbreviation for FKs | `loan_amount`, `fk_loan_id`, `fk_org_id` |
| Layout | `{Table} — {Purpose}` | `Loans — Hub`, `Payoffs — Print` |
| Script | `{verb}_{noun}_{qualifier}` | `record_payment_received`, `generate_payoff_snapshot`, `apply_late_fee` |
| Value List | `vl_{domain}_{name}` | `vl_loan_status`, `vl_payment_method` |
| Custom Function | `cf_{domain}_{action}` | `cf_interest_perdiem`, `cf_days_overdue` |

### Field Patterns (repeating across tables)

| Field | Type | Purpose |
|-------|------|--------|
| `_pk` | UUID / serial | Primary key |
| `fk_*` | text/number | Foreign key (matches parent `_pk`) |
| `created_at` | timestamp | Record creation |
| `modified_at` | timestamp | Last modification (auto-enter) |
| `created_by` | text | Always "Michael" for v1 (single-user) |
| `status` | text (value list) | Record lifecycle state |
| `notes` | text | Free-form annotation |

### UI Principles (from J3)

- **Single operator:** every layout defaults to Michael's workflow
- **Hub-first:** each entity opens to a hub layout showing related portals
- **Dad's views:** read-only dashboard layer, never load-bearing
- **Manual-first:** no automation fires without Michael seeing and approving the output first (v1)
- **Generate-then-review:** all borrower-facing docs are generated by FMP, reviewed by Michael, sent manually

## Declared Workflows

### 1. LOAN ORIGINATION

```
TRIGGER: New loan closes (Christie/Saddle Creek confirms recording)

STEPS:
┌─────────────────────────────────────────────────────────┐
│ 1. [HUMAN] Create Loan record (amount, rate, maturity,  │
│    terms from promissory note)                          │
│ 2. [HUMAN] Create/link Organization record              │
│    (borrower entity, even if individual)                │
│ 3. [HUMAN] Create/link People record(s)                 │
│    (contact info for the humans behind the org)         │
│ 4. [HUMAN] Create LoanProperties join record            │
│    (link loan → property summary)                       │
│ 5. [HUMAN] Create PropertySUMMARY if new property       │
│    (address, parcel ID, type, value at origination)     │
│ 6. [AUTOMATED] Generate ExpectedTransactions            │
│    (interest-only monthly from start → maturity)        │
│ 7. [AUTOMATED] Generate Welcome Packet (from template)  │
│ 8. [HUMAN] Review + send Welcome Packet to borrower     │
│ 9. [HUMAN] Store closing doc links in binder module     │
│ 10. [AUTOMATED] Set maturity alerts (90/60/30 days)     │
│ 11. [EXTERNAL] Christie confirms: recording, insurance, │
│     title policy in place                               │
└─────────────────────────────────────────────────────────┘

INPUTS:
- Signed promissory note (terms)
- Borrower contact info
- Property address + parcel
- Closing docs from title company

OUTPUTS:
- Loan record (active)
- Full ExpectedTransactions schedule
- Welcome Packet (PDF, sent)
- Binder checklist (completeness-tracked)
- Maturity date alerts queued

FMP IMPLEMENTATION:
- Tables: Loans, Organizations, People, LoanProperties, PropertySUMMARIES, ExpectedTransactions
- Layout: Loans — New Loan Wizard (step-through)
- Scripts: create_expected_schedule, generate_welcome_packet, set_maturity_alerts
```

### 2. MONTHLY PAYMENT PROCESSING

```
TRIGGER: Money arrives (check, wire, Venmo) — Michael sees it in bank/Venmo

STEPS:
┌─────────────────────────────────────────────────────────┐
│ 1. [HUMAN] Open Loan hub for the borrower               │
│ 2. [HUMAN] Click "Record Payment"                       │
│ 3. [HUMAN] Enter: amount, date received, method         │
│    (wire/check/Venmo), reference if applicable          │
│ 4. [AUTOMATED] Create ReceivedFunds record              │
│ 5. [AUTOMATED] Match to ExpectedTransaction             │
│    (by loan + period, auto if full match)               │
│ 6. [AUTOMATED] Create PaymentApplication                │
│    (bridge: received → expected, interest-only default) │
│ 7. [AUTOMATED] Update Loan running balance / ledger     │
│ 8. [AUTOMATED] Generate Receipt (from template)         │
│ 9. [HUMAN] Review + send Receipt to borrower            │
│ 10. [AUTOMATED] Mark ExpectedTransaction as satisfied   │
└─────────────────────────────────────────────────────────┘

INPUTS:
- Bank statement or Venmo notification
- Amount, date, method

OUTPUTS:
- ReceivedFunds record
- PaymentApplication record
- ExpectedTransaction marked paid
- Receipt document (generated, sent)
- Loan ledger updated

FMP IMPLEMENTATION:
- Tables: ReceivedFunds, PaymentApplications, ExpectedTransactions
- Layout: Loans — Hub ("Record Payment" button → popover/dialog)
- Scripts: record_payment_received, match_expected_transaction, apply_payment, generate_receipt
- Edge case: partial payment → PaymentApplication splits across periods or holds as unapplied
```

### 3. LATE PAYMENT HANDLING

```
TRIGGER: ExpectedTransaction due date + grace period expires with no matching ReceivedFunds

STEPS:
┌─────────────────────────────────────────────────────────┐
│ 1. [AUTOMATED] Flag ExpectedTransaction as OVERDUE      │
│ 2. [AUTOMATED] Calculate late fee per note terms        │
│ 3. [AUTOMATED] Generate Late Notice (from template)     │
│ 4. [HUMAN] Review Late Notice                           │
│ 5. [HUMAN] Send Late Notice (email)                     │
│ 6. [AUTOMATED] Log communication in comms ledger        │
│ 7. IF still unpaid after X days:                        │
│    [AUTOMATED] Generate Default Notice                  │
│    [HUMAN] Review + escalate (attorney if needed)       │
└─────────────────────────────────────────────────────────┘

INPUTS:
- Loan terms (grace period days, late fee amount/percentage)
- Current date vs. due date

OUTPUTS:
- Late fee applied to loan balance
- Late Notice (generated, sent)
- Default Notice if escalated
- Comms log entry

FMP IMPLEMENTATION:
- Tables: ExpectedTransactions (status field), Loans (late fee accrual)
- Layout: Dashboard — Overdue Queue (filtered list of overdue expected txns)
- Scripts: check_overdue_transactions (scheduled or manual daily run), apply_late_fee, generate_late_notice, generate_default_notice
- Note: v1 = Michael runs the overdue check manually (button). v2+ = scheduled script.
```

### 4. PAYOFF SNAPSHOT (MONTHLY CLOSE)

```
TRIGGER: End of each loan's billing period (per-loan, not calendar month)
         OR: on-demand (borrower asks "what do I owe?")

STEPS:
┌─────────────────────────────────────────────────────────┐
│ 1. [AUTOMATED] Calculate current principal balance      │
│ 2. [AUTOMATED] Calculate accrued interest (per diem     │
│    × days since last payment)                           │
│ 3. [AUTOMATED] Add outstanding fees (late fees, etc.)   │
│ 4. [AUTOMATED] Add wire fee ($10)                       │
│ 5. [AUTOMATED] Create Payoff record (snapshot)          │
│    - good_through_date (typically 10 days out)          │
│    - per_diem_after (daily rate past good-through)      │
│    - total_payoff_amount                                │
│    - payment_instructions (frozen from PaymentInstr.)   │
│ 6. [AUTOMATED] Generate Payoff Letter (from template)   │
│ 7. [HUMAN] Review if sending to borrower                │
└─────────────────────────────────────────────────────────┘

INPUTS:
- Loan balance (principal)
- Interest rate + accrual method (simple, per diem)
- Outstanding fees
- PaymentInstructions (wire info, frozen at generation)

OUTPUTS:
- Payoff record (versioned, immutable once issued)
- Payoff Letter (PDF, ready to send)
- Per-diem rate for days past good-through

FMP IMPLEMENTATION:
- Tables: Payoffs, PaymentInstructions (source), Loans
- Layout: Loans — Hub ("Generate Payoff" button), Payoffs — Print
- Scripts: generate_payoff_snapshot, freeze_payment_instructions, generate_payoff_letter
- Key design: each payoff is a SNAPSHOT (immutable). New request = new record. Version history is automatic.
```

### 5. PAYOFF EXECUTION (LOAN CLOSE)

```
TRIGGER: Borrower sends full payoff amount (wire confirmed)

STEPS:
┌─────────────────────────────────────────────────────────┐
│ 1. [HUMAN] Confirm wire/funds received = payoff amount  │
│ 2. [HUMAN] Record final ReceivedFunds (payoff amount)   │
│ 3. [AUTOMATED] Apply to remaining principal + fees      │
│ 4. [AUTOMATED] Mark all ExpectedTransactions as closed  │
│ 5. [AUTOMATED] Set Loan status → PAID OFF               │
│ 6. [AUTOMATED] Generate Satisfaction Letter             │
│ 7. [HUMAN] Send Satisfaction Letter to borrower         │
│ 8. [EXTERNAL] Christie files lien release with county   │
│ 9. [EXTERNAL] Confirm recording of release              │
│ 10. [HUMAN] Archive loan file (status → closed)         │
│ 11. [AUTOMATED] Remove insurance/maturity tracking      │
└─────────────────────────────────────────────────────────┘

INPUTS:
- Final payoff amount (from latest Payoff record)
- Wire confirmation

OUTPUTS:
- Loan closed (status: paid_off)
- Satisfaction Letter sent
- Lien released (county recording)
- Loan archived

FMP IMPLEMENTATION:
- Tables: Loans (status), ReceivedFunds, PaymentApplications, ExpectedTransactions
- Layout: Loans — Hub ("Close Loan" button → confirmation dialog)
- Scripts: close_loan_payoff, generate_satisfaction_letter, archive_loan
```

### 6. EXTENSION / MODIFICATION

```
TRIGGER: Loan approaching maturity + borrower cannot pay off
         (typically surfaced by 90/60/30-day maturity alert)

STEPS:
┌─────────────────────────────────────────────────────────┐
│ 1. [HUMAN] Borrower communicates inability to pay off   │
│ 2. [HUMAN] Michael decides: extend or demand            │
│ 3. IF EXTEND:                                          │
│    a. [HUMAN] Negotiate new terms (new maturity, fee)   │
│    b. [AUTOMATED] Generate Extension Agreement          │
│    c. [HUMAN] Review + send for signature               │
│    d. [HUMAN] Record signed extension                   │
│    e. [AUTOMATED] Update Loan (new maturity date)       │
│    f. [AUTOMATED] Generate new ExpectedTransactions     │
│       (for extended period)                             │
│    g. [AUTOMATED] Reset maturity alerts                 │
│ 4. IF DEMAND:                                          │
│    a. [AUTOMATED] Generate Demand Letter                │
│    b. [HUMAN] Review + send                             │
│    c. [HUMAN] Escalate to attorney if no response       │
└─────────────────────────────────────────────────────────┘

INPUTS:
- Current loan terms
- New terms (if extending): new maturity, extension fee, rate change if any

OUTPUTS:
- Extension Agreement (signed)
- Updated Loan record (new maturity)
- New ExpectedTransactions (extended period)
- OR: Demand Letter sent → attorney escalation

FMP IMPLEMENTATION:
- Tables: Loans, ExpectedTransactions
- Layout: Loans — Hub ("Extend Loan" button)
- Scripts: extend_loan, generate_extension_agreement, regenerate_expected_schedule
- Note: extension fee = one-time ReceivedFunds entry
```

### 8. BANK RECONCILIATION

```
TRIGGER: Monthly (or as-needed) — Michael reviews bank statement

STEPS:
┌─────────────────────────────────────────────────────────┐
│ 1. [HUMAN] Import or review bank statement              │
│    (BMO Harris + Venmo)                                 │
│ 2. [AUTOMATED] List unmatched ReceivedFunds             │
│    (recorded in FMP but not confirmed on statement)     │
│ 3. [AUTOMATED] List unmatched bank deposits             │
│    (on statement but not recorded as ReceivedFunds)     │
│ 4. [HUMAN] Resolve discrepancies                        │
│    (missing entries, wrong amounts, unidentified deps)  │
│ 5. [AUTOMATED] Mark reconciled period as closed         │
└─────────────────────────────────────────────────────────┘

INPUTS:
- Bank statement (PDF or manual entry for v1)
- ReceivedFunds records for the period

OUTPUTS:
- Reconciled period (all deposits accounted for)
- Discrepancy flags resolved
- Confidence that ledger matches reality

FMP IMPLEMENTATION:
- Tables: ReceivedFunds (reconciled flag), AccountTransactions (bank-side)
- Layout: Reconciliation — Dashboard (side-by-side: FMP ledger vs. bank)
- Scripts: flag_unmatched_deposits, mark_period_reconciled
- v1: manual comparison. v2+: CSV import from bank statement.
```

## Entity Relationship Summary (from J1, J9)

```
People (1 human)
  ↕ [relationship field]
Organizations (1 entity/LLC — ALWAYS faces the Loan)
  ↕ fk_org_id
Loans (1 loan agreement)
  ↕ fk_loan_id
LoanProperties (join: handles 1:1 default + 1:N escape hatch)
  ↕ fk_property_id
PropertySUMMARIES (1 physical property)

Loans → ExpectedTransactions (1:N, one per billing period)
Loans → ReceivedFunds (1:N, one per deposit)
ReceivedFunds → PaymentApplications → ExpectedTransactions (bridge)
Loans → Payoffs (1:N, versioned snapshots)
Loans → LoanDocuments (1:N, binder items)
Loans → CommsLog (1:N, communication history)
PaymentInstructions → Payoffs (frozen snapshot at generation)
GLOBAL_USE_VARIABLES (1 record, app state + config)
```
