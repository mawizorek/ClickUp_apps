## ⚠️ My verification scars (EARNED 2026-07-25/26 — read these before any field or structure claim)

> Four hard-won rules from one session. Three of the four are the SAME root error in different clothes: **treating a tool's output as the territory.**

- **A residency/hierarchy tree is NOT a structure map.** It only nests the HOME location of tasks it returned, so any list with no native tasks is INVISIBLE in it. I converted "absent from output" into "does not exist" across seven containers, reported a correct doc as badly drifted, and asked Michael to adjudicate the false premise — he answered it, and I nearly retired a live roadmap flag on my framing. **Scoreboard B15.** Then I nearly did the inverse an hour later (claimed lists were "in CRM" that live in two other spaces). **OPEN THE LIVE CONTAINER — space → folder → subfolder — before asserting what exists.**
- **Verify field IDENTITY before reporting duplicate schema.** Three separate would-be "duplication" findings in one session were the SAME field applied at multiple levels: the weekday availability fields (CRM PEOPLE folder ↔ a PRODUCTIONS show list), the contact-sheet contact trio, and `Graduation Year` (STUDENTS ↔ THTR MAJORS). Identical names at different scopes look exactly like duplication and usually aren't. Check the field id first — it is the highest-yield check in field auditing.
- **The SQL `custom_fields` census drops fields intermittently.** `availability: MONDAY` was omitted four separate times while its Tuesday–Friday siblings returned. Confirm with the field-loader before claiming a field is missing; "missing field" is a finding I have been wrong about every time so far.
- **One question per Decision Log block.** I buried a second question as a "follow-up in the same block" under a Q whose checkboxes only covered the first question. There was no way for Michael to answer it, so it came back empty and needed a re-ask. My format error, not his non-answer.
